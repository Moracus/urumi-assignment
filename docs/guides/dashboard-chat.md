# Dashboard chat (#41, #42)

Eligible administrators and members open **Chat** (`/chat`) after dashboard login. Each prompt starts a fresh, server-owned conversation; earlier prompts and results are not submitted as browser transcripts. The dashboard displays actual tool-call IDs, public tool names, classified outcomes and the final answer. Calls appear when the request completes, including completed calls when a later provider request fails. Model text is untrusted plain text, without HTML or Markdown execution.

## Provider configuration

Set `OPENAI_API_KEY` in the gateway process environment (the workspace `.env` for host development) and restart the gateway. Never set a `VITE_` variable for this credential. The selected provider is OpenAI, using the pinned `gpt-4.1-mini-2025-04-14` model and the HTTPS Chat Completions endpoint at `https://api.openai.com/v1/chat/completions`. The implementation sends function tools and assistant `tool_calls`, then supplies one `role: tool` result for each originating `tool_call_id`, as described in [OpenAI's function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling). Requests set `store: false`; provider data handling remains subject to your OpenAI account policy.

Absent, blank or malformed keys leave chat unavailable. A rejected credential, provider outage, malformed response or exhausted execution limit stops the request with a safe error. Existing management and MCP features remain usable. The browser's authenticated `GET /api/chat` reports only availability; it does not test provider connectivity or return configuration. `POST /api/chat` accepts exactly `{ "prompt": "..." }` with JSON content type and the existing dashboard session, trusted Origin and CSRF header. Bearer keys cannot substitute for a dashboard session. Identity claims and browser transcripts are rejected.

The optional `createGatewayApp({ chat: { apiKey, endpoint } })` endpoint override exists for deterministic HTTP fixtures; there is no browser or environment endpoint override. Ordinary runtime uses the fixed HTTPS provider destination. Helm Secret references and provider egress approval are a separate dependent rollout slice: this change does not configure Kubernetes access, open egress, or establish a live provider deployment. Configure no raw credentials in committed Helm values. Existing dashboard ingress already routes `/api` to the gateway.

## Permissions and execution

Every model turn derives its tool definitions from the current authorized discovered catalog. Sorted catalogs use deterministic `tool_0`, `tool_1`, … aliases, with a request-local mapping to discovered public names. Names differing only in punctuation or exceeding provider limits remain distinct. Tool descriptions and schemas are passed as untrusted data, with known credentials redacted. Aliases from one provider response are resolved against that response's offered catalog, never by splitting invented names.

Before each call the gateway reauthenticates the dashboard session, checks current eligibility and permissions, and validates arguments using the current discovered JSON schema and the MCP SDK's validator. It reauthenticates immediately before `executeTool`, which independently authorizes, resolves and invokes through the existing registry and ten-second upstream timeout. Removed, disabled, unreachable or replaced registrations cannot execute through a stale provider alias. Role or session changes stop or deny subsequent calls. These checks enforce security even if model instructions or upstream text are malicious.

Members retain the existing WooCommerce read permissions and calculator/time tools. Administrators may use registered write tools. Tools act against shared upstream store authority: permitted calls may read or change shared store data. Prompt instructions do not create isolation or authorization. Provider and resolved upstream credentials remain on the server; known raw credential values are redacted from provider-visible text and browser answers. Do not put credentials in prompts, upstream schemas or business data; arbitrary transformed secrets cannot be reliably identified by text redaction.

Execution audits use the verified user ID/email, `authenticationOrigin: dashboard_session`, and `keyId: null`. Invalid schema arguments, stale aliases and forbidden attempts have rejection rows; invented aliases use a fixed unknown-tool label instead of arbitrary model input. Successful results and valid MCP `isError` results remain distinct. Raw arguments and result bodies are not written to audit history. Audit failure emits the existing sanitized operational signal and never replays a tool; rows cannot be guaranteed during MongoDB failure.

## Bounds and recovery

Each request is limited to a 16 KiB HTTP body, a trimmed 1–8000-character prompt, five provider requests, eight proposed tool calls, 128 catalog entries, 128 KiB encoded provider context (including tool definitions), 16 KiB per encoded tool result, 256 KiB per provider response and 2048 provider output tokens. Provider requests, including response reads, have a 20-second timeout. The overall deadline is 90 seconds; no new tool starts with less than 12 seconds remaining. An already-started invocation/audit may finish after the deadline. Disconnects abort provider I/O and prevent subsequent tool calls; they cannot undo an upstream side effect already in progress. An oversized UTF-8 tool result stops the conversation immediately, including any remaining calls in the same provider response. The displayed execution outcome remains truthful: the tool already ran. No further provider request is made with the oversized result.

No provider or tool requests are retried automatically. Duplicate call IDs stop the loop before dispatch. Equivalent JSON arguments (including reordered object properties) for the two known WooCommerce write tools are suppressed within a prompt. A write tool error or uncertain execution failure blocks all further writes in that prompt; this is not cross-request idempotency. Review displayed calls and administrator tool history before deliberately resubmitting after any error or disconnect: a write may already have completed. The form never automatically resubmits. Context, timeout, access-change and limit failures preserve completed-call outcomes when the browser is still connected. Limit errors identify the exhausted context, result, provider-response, catalog, call, turn or duration budget; provider timeouts are identified separately. Cancellation and the duration reserve are checked again after the final asynchronous authentication, immediately before dispatch. Operational failures emit only a fixed `chat_failed` event, request ID and classified reason, without raw provider responses or exceptions. Live provider acceptance remains an operator check.

## Example prompts and validation

- As a member: “Multiply 6 by 7 and tell me the current time in Asia/Kolkata.” This should use calculator and time tools.
- As an administrator: “Create a product named Demo Mug priced at 12.50 with status=publish.” Inspect the storefront before repeating a failed request.
- For orders: “Get today's orders for Asia/Kolkata, using local midnight to the next local midnight as the date range.” Supply a timezone explicitly and inspect returned boundaries; date conversion is performed by the model, not a dedicated verified date module.

Gateway tests in `apps/gateway/src/app.test.ts` run actual provider HTTP encoding against a deterministic HTTP fixture, a running gateway, disposable replica-set MongoDB and controlled MCP upstreams. They cover role-filtered catalogs, punctuation/long-name aliases, schemas, call/result IDs, multiple upstreams, MCP tool errors, safe failures, session revocation, no write replay and session audit attribution via the administrator API. `apps/dashboard/tests/chat.spec.ts` covers calls/outcomes/answers, plain-text rendering, provider failure, expiry and unconfigured chat. Run `pnpm test:workflow` for the full automated gateway/browser workflow. These fixtures do not prove paid-provider access, storefront mutations or a deployed network policy; those require explicit operator checks after rollout.

## Regression evidence (#42)

Deterministic provider HTTP fixtures withdraw roles, account eligibility, password eligibility, session validity and live server registrations during a running request. Tests exercise account/session changes between calls in one response and between model turns, and disable/remove registrations through the management API both between turns and during a multi-call provider response. Old aliases cannot retain authority. Additional cases cover UTF-8 body/result/provider-response budgets, context growth, call/turn/catalog exhaustion, provider authentication/malformed/outage/timeout failures, overall elapsed time, disconnects and actual upstream side-effect counts after uncertain writes. Failed calls retain their original provider IDs when error feedback is sent. Browser tests cover a later provider failure and expiry inside the loop while retaining completed-call outcomes.

Authentication and registry checks admit individual calls; they do not roll back an already admitted operation when access changes. The overall deadline bounds admission and provider I/O; an admitted upstream call uses its existing ten-second timeout, and execution/audit or database operations already in progress may finish later. Inspect tool history and store state before deliberately retrying any uncertain write. There is no automatic resume or cross-request idempotency guarantee.
