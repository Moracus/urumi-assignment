# Durable tool history (#39, #40, #52)

The application defaults to MongoDB audit storage through the existing `AuditLogger` contract and identity connection lifecycle. Startup creates `tool_audit` and its unique attempt-ID and descending `(timestamp, _id)` indexes before serving traffic. History survives gateway restarts; it is independent of console-log retention. `ConsoleAuditLogger` remains an explicit development/test option, not the application default.

Eligible administrators can open **Tool history** at `/admin/audit`. The table shows User, Server, Tool, Time, Duration and Outcome, with expandable **Attempt details**, loading, empty, refresh, retry and previous/next states. Details show existing attempt/request correlation IDs, authentication origin, user/key IDs and historical user/server snapshots. Outcome explanations distinguish valid MCP tool errors, rejected calls and upstream failures without guessing underlying error causes. Members do not see the link and cannot access the API. Session expiry, permission loss and required password replacement use the dashboard's existing session reset behavior and discard protected data and delayed responses. Refresh failures retain only the last successful authorized read with an explicit stale warning; changing filters or pages clears the previous view.

`GET /api/admin/audit?page=1&limit=20` uses the existing dashboard cookie, HTTPS and backend administrator guards. Bearer-only or unauthenticated requests receive 401; eligible members receive 403. Responses use `Cache-Control: no-store`. Parameters are strict decimal integers: page defaults to 1 (maximum 2147483647); limit defaults to 20 (maximum 100). Unknown, duplicated and invalid query parameters receive 400. The dashboard uses ten rows per page. Optional API filters are `userId` and `upstreamId` (canonical lowercase 24-character hexadecimal IDs), `toolName` (exact public name, 1–512 characters), `outcome` (one classified outcome), `from` (inclusive) and `to` (exclusive). Times must be ISO datetimes with a timezone; offsets normalize to UTC. Reversed/empty time ranges and invalid filters receive 400. Filters combine with AND and retain the same pagination/order. The interface exposes these filters and stores them, plus the page, in `/admin/audit` query parameters. Apply/Clear resets to page 1; direct links restore filters, canonicalize time offsets to UTC and preserve native Back/Forward navigation without a routing migration. The UI uses a fixed ten-row page size (`limit` is an API-only parameter); invalid/unknown/duplicate deep-link inputs show a filter error without fetching history. Clear filters recovers from invalid links. Time inputs accept ISO datetimes with an explicit timezone, not ambiguous local times. URL filters contain no credentials, but can contain user IDs and tool names; share links only with intended administrators.

`upstreamId` matches the stored registration document ID exactly, including deleted registrations. A replacement using the same public server name has a new ID and separate history. Copy the Registration ID from Attempt details to investigate that instance; no current-registration join or tool-name splitting is used. Rows with null upstream attribution never match a registration filter. Server labels and emails are historical snapshots, not current account/registration labels.

The response is `{ records, page, limit, hasMore }`. Rows are ordered by timestamp descending, then MongoDB row ID descending for deterministic timestamp ties. A limit-plus-one query determines `hasMore` without counting all history. Offset pages are live views: concurrent new attempts can move rows between pages; this API does not promise a snapshot or cursor. Large offsets become more expensive.

Each row explicitly projects these fields:

| Field | Meaning |
| --- | --- |
| `id` | Durable MongoDB audit row ID and ordering tie-breaker |
| `attemptId` | Server-owned UUID for this attempt, shared by ingress and execution |
| `requestId` | Caller request correlation for internal execution; identifiable MCP calls use the server-owned attempt UUID, never the client RPC ID |
| `userId`, `userEmail` | Verified user ID and minimal historical email snapshot; both null for unauthenticated calls (email may also be null for legacy internal identities) |
| `authenticationOrigin` | `gateway_api_key`, explicit `dashboard_session`, or null when authentication did not establish an identity |
| `keyId` | Actual gateway API-key ID for verified bearer execution; null for dashboard sessions and unauthenticated attempts |
| `upstreamId`, `upstreamName`, `upstreamDisplayName` | Registration document ID, public server ID and historical display name, when known; unresolved upstreams stay null |
| `toolName`, `timestamp`, `durationMs`, `outcome` | Public tool name, UTC attempt start, elapsed duration, classified outcome |

`AuthenticatedIdentity` accepts legacy bearer identities with a real `keyId`; bearer authentication now explicitly sets origin and email from the database. A dashboard caller must construct a server-verified identity with `authenticationOrigin: "dashboard_session"` and `keyId: null`. Session identity cannot be used to authenticate `/mcp`. This slice adds the shared contract, not a chat execution endpoint. Permissions still run through `executeTool()` before resolution and invocation.

User display attribution is captured at authentication. For a resolved upstream, the registration ID/display snapshot is read before invocation, so later edits/removal do not rewrite the row. Display snapshots do not depend on mutable joins. A failed attribution lookup emits a fixed operational message and leaves unavailable metadata null; it does not repeat tool execution.

Execution outcomes are `success`, `tool_error` (valid MCP `isError`), `unauthorized`, `not_found`, `upstream_error`, `upstream_unavailable`, and `upstream_timeout`. Valid MCP structured results are returned unchanged. Persisted/public audit fields exclude credentials, key hashes, session tokens, tool arguments, result bodies, internal URLs and exception stacks. Raw errors are never serialized to audit storage. Emails and tool/server display labels are retained intentionally as historical attribution; administrators can read them.

## Rejected MCP attempts

The `/mcp` ingress recognizes a single POST JSON-RPC 2.0 `tools/call` request with a string or finite numeric ID and an object `params` containing a name of 1–512 ASCII letters, digits, underscores, hyphens or dots. It creates a UUID before authentication. Client RPC IDs, `_meta`, user/role/key claims and supplied attempt IDs cannot set audit identity or deduplication. Reusing the same RPC ID produces separate attempts, including concurrent calls.

| Rejection outcome | Meaning |
| --- | --- |
| `unauthenticated` | No verified identity: missing, invalid or revoked bearer credential, or authentication could not establish identity. User/email/key/origin and all upstream fields are null. |
| `not_found` | Authenticated call names no tool in the current available catalog. No upstream is inferred from the name. |
| `unauthorized` | Authenticated identity cannot invoke a known catalog tool under the existing backend role policy. |
| `rejected` | Known, permitted tool never reached its execution callback: includes SDK argument/schema validation and protocol/dispatch rejection. This deliberately does not classify such failures as upstream failures or valid MCP tool errors. |

The SDK retains ownership of validation, dispatch and Streamable HTTP responses, including legacy SSE and current protocol clients. Authorization filtering still hides forbidden tools; actual execution still authorizes independently. Ingress passes the server-owned UUID into execution and relinquishes recording as soon as the callback starts. Execution records the determined outcome once; otherwise ingress attempts one fallback insert after HTTP handling. The unique MongoDB attempt-ID index also prevents duplicate durable rows. No failed audit insert is retried by the other layer.

Rejected rows retain verified user/key attribution only after successful authentication and leave upstream metadata null because resolution/invocation was never reached. SDK error text, raw arguments, malformed payloads, headers and credentials are never copied to history. A denial can reach its HTTP client before the fallback audit write completes; history is observable after that bounded write completes. Graceful shutdown drains pending fallback audit writes before closing MongoDB.

Malformed JSON, oversized bodies rejected by Fastify (the existing 1 MiB limit), missing/null IDs, notifications, non-tool methods, batches rejected before callbacks, missing names, and names outside the bounded format do not produce synthetic rejection rows. Host/content-type/parser rejections before the route likewise create no rows. Valid calls reaching execution still record there, including supported batch calls. This is bounded tool-attempt coverage, not a log of all HTTP traffic. Authentication outages can also prevent audit persistence; no verified attribution is guessed.

## Storage failure and rollout

An audit-write failure never replaces an already determined result/error and never triggers another upstream invocation. The server emits only `{ "event": "audit_write_failed", "attemptId": "…" }` on stderr. Monitor this event alongside the fixed MongoDB connection/attribution failure messages. A MongoDB driver write may take up to the existing bounded storage timeout; result delivery can wait for that write attempt. There is no durable queue or replay. Missing rows during rejected writes or storage outages are possible and are not backfilled. A lost acknowledgement can also leave uncertainty about whether a row committed. New requests still fail existing authentication checks during a full database outage.

Rebuild and roll out the gateway and dashboard images together using the existing deployment procedure. No new environment variables, Secrets, Helm values, Services, PVCs or network permissions are required. Existing MongoDB privileges must permit collection/index creation and audit insert/read, as they already do for identity collections. Do not reset MongoDB or application volumes. No automatic retention policy or TTL is added: operators must plan retention and backups for growing history. Console records from earlier versions are not imported.

## Administrator observability (#53, #54)

`/admin/observability` and `GET /api/admin/observability` use the same eligible administrator session guard as history, with `Cache-Control: no-store`. Anonymous, bearer-only, member and required-password-change sessions cannot read global metrics. The member overview does not request them.

The strict query accepts `preset=hour|day|week` (default day), or both `from` and `to` ISO datetimes with explicit timezone, plus optional canonical lowercase 24-hex `upstreamId`. Explicit bounds cannot combine with a preset. Offsets normalize to UTC; from is inclusive, to exclusive; the maximum span is seven days. Unknown, repeated, empty and reversed inputs return 400. Presets end at generation time. Explicit windows may query older history and are not restricted to the last seven calendar days.

The runtime-validated response is `{ from, to, generatedAt, bucket, percentileMethod, rows }`. Each row has `kind` (`registration`, `legacy`, `unattributed`), nullable `upstreamId`, distinct `historicalNames` snapshots, nullable `current` (`name`, `displayName`, `status`), `outcomes` (all nine classified counts), `attempts`, `failures`, and nullable `errorRate`. For durable registrations, attempts = success + tool_error + upstream_error + upstream_unavailable + upstream_timeout. Failures are the last four terms; errorRate = failures / attempts, or null without samples. Rejected, unauthorized, not_found and unauthenticated are separate counts, excluded from that denominator. Legacy name-only and unattributed groups retain their outcome breakdown but have zero attributed attempts and no per-registration rate. These are recorded gateway attempts; some failures happen before reaching an upstream. Audit-write outages, lost acknowledgements, bounded ingress coverage and missing backfill described above apply equally to these counts. No coverage estimate is inferred.

MongoDB matches the window and optional registration, then groups all matching audit rows before applying any response cap. Counts, durations and trends share one `$facet` input stream so audit inserts cannot create different populations across those metrics. It never counts a browser page. Queries use a five-second execution limit and disallow aggregation disk spill. The existing timestamp index serves global windows; the added `(upstreamId ascending, timestamp descending)` index serves registration windows. There is no raw-row limit. Up to 4,500 distinct registration/name-snapshot/outcome groups and 500 response rows/current registrations are allowed. Exceeding a cap fails the complete read with 503; no partial counts are returned. Grouped labels and IDs are runtime bounded, limiting response size. Query failure is separate from upstream health.

Current zero-activity registrations appear. Historical IDs survive removal and never join a replacement solely by name; runtime health matches both durable ID and configuration revision. Historical names stay alongside current labels. Reads of audits, durable registrations and runtime health are adjacent observations, not a transactionally frozen snapshot.

The page offers sortable rows, manual refresh, and a 60-second visible-page timer. Visibility restoration requests a read. Cleanup, pending-read exclusion, discarded superseded responses and the shared session generation prevent overlapping refreshes and stale responses from repopulating protected data. Last successful generation time and effective UTC bounds remain visible on explicitly stale authorized reads. Session/permission loss clears protected data. Refresh never invokes tools, discovery or reconnection. Deploy rebuilt gateway and dashboard together; no infrastructure or environment changes are required. Collection startup creates the additive index; large existing collections may require operator scheduling for index creation.

### Recorded execution durations and activity trends (#54)

Each row adds `durationSampleCount`, nullable `averageDurationMs` and `p95DurationMs`, `timeoutCount`, and `trend`. Primary duration samples are finite, nonnegative recorded `durationMs` values on **success or tool_error** records belonging to that durable registration ID. Name changes share one population; removed/recreated registrations do not. The average is the sum of those durations divided by their sample count. p95 is MongoDB's `$percentile` accumulator with `p: [0.95], method: "approximate"`; the response labels `percentileMethod: "approximate"`. MongoDB uses t-digest, and results can vary between runs, particularly for duplicate values. Tests use a known 1–1,000 ms population with a ±20 ms tolerance around 950 ms, plus exact constant-population assertions. This is a descriptive statistic, without a confidence or completeness guarantee. See the [MongoDB percentile documentation](https://www.mongodb.com/docs/v8.0/reference/operator/aggregation/percentile/).

The operator requires MongoDB 7.0 or newer. The chart and disposable integration harness both target MongoDB 8.0; the local deployed `urumi-mongodb-0` binary was checked as **8.0.34** during implementation. Real-storage API tests execute the operator on the disposable MongoDB 8 image. Operators supplying an external database must verify version compatibility before deploying this slice; unsupported/query-failed reads fail safely rather than returning zero durations.

`durationMs` measures gateway execution from entry to `executeTool()` through authorization, resolution, attribution and invocation/outcome handling, stopping before audit insertion. It includes that gateway work and excludes waiting for the audit insert. It is neither upstream-only latency nor end-to-end HTTP response time. Ingress rejection timings, unauthorized/not-found outcomes and transport errors do not enter primary duration samples. `timeoutCount = outcomes.upstream_timeout` is displayed separately, and timeouts remain in attributed failure counts. No automatic retries are introduced. Zero-duration **recorded samples** are valid; missing samples return null, shown as an em dash (—) along with absent rates. Legacy/unattributed rows have no primary registration-duration population.

The strict query also accepts `bucket=5minute|hour|day`. If omitted, spans up to one hour use five minutes, spans up to 24 hours use one hour, and longer spans (at most seven days) use one day. These defaults apply to explicit historical windows as well as presets. Unknown, empty, repeated and unsupported bucket values return 400. More than **169 buckets per row**, including partial edges, returns 400. A report exceeding **12,000 total zero-filled row/bucket points**, 500 rows/current registrations, 500 duration groups, 4,500 name/outcome groups or 12,000 nonempty trend groups fails the whole read with 503. No partial aggregates or raw audit pagination feed these metrics. One bounded five-second aggregation, without disk spill, computes the complete window before result caps. MongoDB aggregation/facet memory and document-size limits can also fail a read safely.

Bucket interiors align to UTC epoch multiples of five minutes, one hour or one day. The first/last reported bounds are clipped to the effective `[from, to)` window; every point exposes UTC `from` inclusive and `to` exclusive. A record exactly on an interior boundary belongs to the following bucket, and a record at the window's `to` is excluded. Every row includes all buckets, with zero counts for inactivity. Each point exposes all nine `outcomes`, attributed `attempts`, `failures` and `timeoutCount`, using the same registration attribution and outcome formulas as the full row. Zero activity means no recorded attempts, without implying healthy service. Legacy/unattributed groups retain their bucket outcomes while attributed attempts/failures stay zero.

The dashboard provides bucket selection and expandable, captioned activity tables with outcome distinctions and focusable horizontal scrolling. Keyboard and 360/768/1440-pixel browser journeys exercise the tables. Changing window/bucket/registration discards superseded results; refresh remains read-only. Audit coverage limits above apply: lost writes, outages, bounded ingress coverage and no backfill make these **recorded** samples, not a complete traffic or availability measure. Deploy rebuilt gateway and dashboard together; there are no new environment variables, storage migrations or Helm changes.

### Linked investigations (#56)

Inspection (`/admin/servers`), observability (`/admin/observability`) and history (`/admin/audit`) exchange `upstreamId` and canonical UTC `from` inclusive / `to` exclusive bounds. Server inspection decodes the API's `registrationId` as that durable identity, resolves the current public name through the authorized list and verifies the returned detail identity before showing it. A removed ID opens a historical-registration panel with activity links; it never opens the replacement by matching a name. Display-name edits leave the ID and historical labels intact. Legacy/name-only and unattributed metrics stay separate and have no registration links.

Opening inspection or metrics without bounds captures the preceding 24 hours once. Choosing a relative preset captures a fresh concrete window in the URL. Refresh, the visible-page timer and switching views keep those bounds fixed. Choose a preset again to advance the window. Metrics require both bounds and at most seven days; history remains able to query wider or open-ended ranges, but asks for a bounded range before offering comparison links. Bucket selection is shareable on observability; linked history uses each trend point's actual clipped bounds, independent of bucket presentation. Back/Forward restores selection, filters and bounds, and changing history filters resets to page 1. Invalid investigation URLs show a recoverable error; invalid metrics URLs issue no metric read.

Metric totals link to matching history at page 1, with no user/tool narrowing:

| Metric link | History population |
| --- | --- |
| Attributed attempts | `activity=attempts`: success, tool_error, upstream_error, upstream_unavailable, upstream_timeout |
| Failures | `activity=failures`: the same population excluding success |
| Duration samples | `activity=durations`: finite nonnegative duration samples on success and tool_error |
| Timeouts | `outcome=upstream_timeout` |
| Outcome count | The exact `outcome` |
| Trend count | The corresponding population and the point's `[from, to)` |

`GET /api/admin/audit` adds optional `activity=attempts|failures|durations`. Activity filters require durable attribution and combine with **all** other filters using AND, including an exact outcome; an incompatible outcome produces an empty result. Unknown activity values are rejected. Existing authentication, authorization, ordering and pagination are unchanged. A metric link's count may span multiple ten-row history pages.

Metrics remain registration-wide. A link from history preserves exact user/tool/outcome/activity filters as navigation context, explicitly says that those filters do not narrow metrics, and offers **Resume exact history filters**. Selecting a metric total deliberately replaces that context with the metric's population so the linked rows match the displayed number. Inspection preserves the exact context too. URLs carry no credentials or payloads, but IDs and tool names are administrator information.

These are adjacent live reads, not a frozen database snapshot. Fixed bounds prevent the window from moving, but late audit writes can change totals or pages within it; there is no backfill or completeness guarantee. Previously described duration/rate formulas, approximate p95, storage/query limits, diagnostic limits and uncertain-write guidance still apply. Refresh and ordinary navigation never execute tools, reconnect, rediscover, or replay mutations. Authorized stale results and their original bounds remain usable after a read failure. Session generation changes discard protected data and delayed reads; backend administrator checks remain authoritative.
